# 失败案例

> 只记录**真实发生过、有日志可查**的失败；每条包含：现象 → 证据 → 根因 → 处置 → 教训。
> 与 `docs/deployment.md` 的踩坑表互补：那里记操作坑，这里记评测/推理层面的失败。

---

## 案例 1：首次基线评测，后三档全部失败

**现象**：`E00_BASELINE_PERF_20261031_053524` 的四档里，c1 只有 23 条有效记录，c2/c4/c8 完全没产出
`profile_export_aiperf.json`，`summary.json` 的 `status` 全是「异常」。

**证据**（`experiments/E00_BASELINE_PERF_20261031_053524/performance/c2/console.log`）：

```
ERROR    All 100 inference request(s) failed; no successful responses were collected.
WARNING  ColumnStore.numeric: unknown tag 'input_sequence_length' on a non-empty store
╭─ AIPerf System Exit Errors ─╮
│    Error: Unknown            │
```

**根因**：评测启动时推理服务并未真正就绪（端口在、模型未加载完成 / served-name 不匹配），
AIPerf 发出的 100 个请求全部失败；它把失败样本当成"没有数据"，于是 `summary.json` 缺字段。

**处置**：
1. 重启服务，等 `/v1/models` 返回 `max_model_len` 后再开跑；
2. 重跑得到 `E00_BASELINE_PERF_20261031_055409`，四档全部 `status=完整`、每档 100 请求；
3. 在 `scripts/start_model.sh` 里加了"等服务就绪"的等待，并把 curl 探活写进启动流程。

**教训**：**评测前必须做前置检查**（服务就绪 + GPU 独占 + 端口空闲），
不能"启动了就开始压"。这条后来固化成 `/api/benchmark/pretend` 与 `experiment_manager.preflight()`。

## 案例 2：精度评测卡死 26 分钟

**现象**：`E00_BASELINE_ACC2_20261031_081016` 跑到 87/100 后停住，
26 分钟内预测文件不再增长，GPU 仍显示 100%，但引擎不再输出生成记录。

**证据**：

| 时间 | 观测 |
|---|---|
| 18:16 | 预测条数 87，之后一直是 87 |
| 18:16–18:42 | GPU 利用率 100%，显存 42.9 GiB 不变 |
| 引擎日志 | 生成吞吐记录停在 `10:43:04`（UTC），之后只剩 `GET /metrics` 探活 |
| 客户端 | 评测进程仍在，但无新请求完成 |

**根因**：未完全定位。可能是超长思考样本（该数据集最长输出 69,126 字符，接近 `max_tokens=32768`）
与引擎调度叠加导致的实际 hang；**引擎日志停止输出生成记录**是关键线索，说明不是"在慢慢生成"。

**处置**：
1. 杀掉评测进程与 evalscope，保留已生成的 87 条（**按规则不作为成绩**，因为不足 100）；
2. 切换到优化实验（GPU 优先给 40 分那项）；
3. 精度重跑改为 `eval_batch_size=4`（更快），并**加看门狗**：`scripts/watchdog_accuracy.sh`
   监测预测文件 mtime，超过 15 分钟无增长就杀进程并记录原因。

**教训**：**长时间无人值守的任务必须有看门狗**，判断依据要用"产物是否增长"而不是"GPU 是否忙"——
这次 GPU 一直显示 100%，恰恰是最容易骗过人的指标。

## 案例 3：后台等待链超时后"往下走"，把正在跑的服务杀了

**现象**：跑了 45 分钟的 IFBench 在 35/100 时中断，vLLM 收到 SIGTERM 并优雅退出。

**证据**（`/root/logs/night_pipeline.log`）：

```
[06:08:02] === 等待 E00 流水线结束 ===
[08:08:03] === 阶段 3+4：AutoTuner 网格（6 个候选）===
```

等待循环写成 `for i in $(seq 1 240); do grep -q '完成' && break; sleep 30; done`，
240 次 × 30 秒 = 2 小时后循环自然结束，**没有 `break` 也会继续执行后面的 stop/start**。

**处置**：停掉所有长驻等待链；改成一阶段一推进，并把等待条件改成**文件存在性**而非字符串匹配；
超时一律 `exit`，不 fall-through。

**教训**：**等待循环必须"条件不满足就失败"**，而不是"等够时间就继续"。
这条现在写进 `scripts/optimize_pipeline.sh`：`[ -f summary.json ] || exit 3`。

## 案例 4：MTP 投机解码的"无限思考循环"（文档记载，待本轮验证）

**现象**（比赛提供的基准文档记载）：FP8 + MTP 在部分指令上会持续输出思考内容，
直到撞上 `max_tokens` 上限，表现为"同一题耗时数分钟、输出被截断"。

**本项目的处理**：
1. 默认**不开** MTP（`configs/runtime.json` 的 `baseline` profile 无 `speculative_config`）；
2. 单独排一组 `mtp_on` 对照，同时采集：是否触发 `max_tokens`、平均输出长度、IFBench 是否完整；
3. 若复现，则判定"加速收益不可用"，保留基线配置并把现象写入本节。

**当前状态**：`mtp_on` 候选已排队（第 3 组）。若本轮未复现，会如实写"未复现"，
而不是把文档记载当成自己的发现。
