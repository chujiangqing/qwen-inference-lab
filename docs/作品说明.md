## 1. 项目概述

**解决什么问题**：在一张消费级显卡（RTX 4090，48 GiB 魔改版）上，把 30.9B 稠密参数的
Qwen3.8-27B（FP8）跑到接近硬件极限，并且能证明"加速没有牺牲质量"。

**最终做出了什么**：

| 交付物 | 内容 |
|---|---|
| 一套可复现的部署与评测平台 | 启动/停止/评测/优化全脚本化，FastAPI + 9 页前端 |
| 一份真实基线 | 4 档并发 × 100 请求，输入精确 8192 token，全部 `status=完整` |
| 一组受控优化实验 | 7 组单变量 + 2 组双因子组合（MTP 与并发上限） |
| 一个可解释的瓶颈结论 | 用实测 TPOT 反推权重读取带宽，判定"单请求已到带宽上限" |
| 质量证据 | IFBench 100 题 + 三类任务（长文本/逻辑/代码）自动判分抽检 |

---

## 2. 问题与目标

**为什么值得解决**：27B 级模型在 48 GiB 单卡上属于"刚好装得下"的临界场景——权重 28.75 GiB、
剩下的显存要同时喂 KV Cache 和框架开销。这类场景的调参经验很难迁移，必须实测。

**成功标准（事先定好，避免事后找补）**：

| 维度 | 标准 |
|---|---|
| 装得下 | 权重 + KV + 框架开销 < 48 GiB，且能稳定跑满 4 档并发 |
| 更快 | 输出吞吐相对基线提升 ≥10%，且延迟不出现不可接受的恶化 |
| 不掉质量 | IFBench 分数不低于基线的 1 个标准误（±4pp） |
| 可复现 | 从零到跑通有明确步骤与成功标志；评测脚本零改动 |

### 3.1 模型 / 版本 / 来源 `[评分表补充]`

| 项 | 值 | 怎么核验 |
|---|---|---|
| 模型 | Qwen3.8-27B（架构 `Qwen3_5ForConditionalGeneration`） | `grep architectures config.json` |

| 版本标识 | 该快照**没有** git commit 元数据，改用文件指纹：`config.json` sha256 `74227dd615bf1ea9…`、`index.json` sha256 `f0838c766951bdfe…` | `sha256sum config.json` |
| 结构 | 64 层 = 48 层线性注意力 + 16 层全注意力；含 MTP 层（22 张量）与视觉塔（333 张量） | 按 index.json 张量名统计 |

**第三方佐证**：主办方提供的《Qwen3.8-27B 基准测试》文档里，参考实现用的正是

--max-num-seqs 4 --gpu-memory-utilization 0.90`，MTP 为注释状态）。我们在本机按同一配置复现，
四档吞吐相对偏差 **0.2%–0.7%**（见 §5.1 与 §5.2 对照），说明版本与口径对得上。

### 3.2 显存预算（实测，非估算）`[评分表补充]`

| 项 | 数值 | 来源 |
|---|---:|---|
| 显存总量 | 48 GiB（49140 MiB） | `nvidia-smi` |
| 权重 | 28.75 GiB | 按 index 清单统计（排除子目录） |
| 可用 KV Cache | 11.56 GiB | vLLM 启动日志 `Available KV cache memory` |
| 运行期总占用 | 42.5 GiB | `nvidia-smi` 评测期间采样 |
| 余量 | 约 5.5 GiB | 差值 |
| KV 单位成本 | **32 KiB/token**（只有 16 层全注意力存 KV，fp8） | 2 × 16 × 4 头 × 256 dim × 1 B |
| KV 容量（40960 上下文） | 299,132 token，并发上限 **7.30×** | vLLM 日志 `GPU KV cache size` |
| KV 容量（16384 上下文） | 231,303 token，并发上限 **14.12×** | 同上 |

**为什么这个预算能成立**：48 × 0.9 = 43.2 GiB 可用；减去权重 28.75 与框架开销约 1.5，
剩约 12.9 GiB 给 KV；vLLM 实际分配 11.56 GiB，与预算一致（差 10%）。

### 3.3 方案对比（一）：量化路线 `[评分表补充]`

#### 3.3.1 两条路线的可行性

| 路线 | 规则原文 | 本机可行性 | 依据 |

### 4.3 五条优化路线的覆盖情况

评分表给了五条路线，不是要求全做，而是要求"思路清晰 + 针对瓶颈 + 有取舍依据"。

| 路线 | 本项目做了什么 | 证据 | 没做的原因（同样有据） |
|---|---|---|---|
| **量化** | KV Cache `fp8` 与 `bf16` 对照 | 66.26 vs **64.81** tok/s，bf16 慢 2.2%、TTFT +19% | 权重层 PTQ 不做：BF16 权重 52 GiB 装不下、工具链不覆盖该混合架构；规则明确「量化非必选，未量化不扣分」 |

| **KV cache / 批处理** | 同上 + KV 容量与并发上限实测 | 40960 上下文 299,132 token / 7.30×；16384 上下文 231,303 / **14.12×** | — |

### 4.4 七组单变量实验（20 请求/档）

| 候选 | 吞吐 tok/s | TTFT P95 ms | TPOT P95 ms | 显存 GiB | 相对基线 |
|---|---:|---:|---:|---:|---:|
| 基线（100 请求/档） | 66.26 | 36,374 | 52.9 | ~42.5 | — |
| **mtp_on** | **91.79** | **11,505** | **47.4** | 42.28 | **+38.5%** |
| ctx16384_seq8 | 84.95 | 24,878 | 78.5 | 42.07 | +28.2% |
| ctx16384_seq16 | 84.86 | 24,924 | 78.5 | 42.09 | +28.1% |
| seq8_tok16384 | 84.79 | 26,407 | 60.3 | 46.59 | +28.0% |
| seq8_tok8192 | 84.78 | 26,074 | 71.5 | 44.43 | +28.0% |
| seq4_tok2048 | 66.16 | 42,145 | 52.8 | 42.10 | −0.2% |
| kv_auto（bf16 KV） | 64.81 | 43,403 | 54.1 | 41.73 | −2.2% |

三条可读出的机制（不是罗列数字）：

1. **MTP 是唯一"吞吐与延迟同时改善"的配置**（TPOT 反而降 10%）——它减少的是"每 token 的权重读取"，不是靠排队换吞吐；
2. **并发 8 的三组（84.78 / 84.79 / 84.95）几乎相同**，说明收益来自 `max_num_seqs` 4→8 本身，上下文长度与 prefill 批大小都不是性能因子；
3. **prefill 批两端都不划算**：调小（2048）拖慢 TTFT 83%，调大（16384）多吃 2.2 GiB 显存、吞吐不变。

### 4.5 双因子（MTP × 并发上限）

|  | 4 路 | 8 路 |
|---|---:|---:|
| MTP 关 | 66.26 | 84.78 |
| MTP 开 | 91.79 | 待填（组合 B） |

交互项 `I =（开 MTP 后提并发的增量）−（关 MTP 时提并发的增量）`，待填。
预计 `I < 0`：两个优化都在"摊薄每次权重读取"，后加的边际收益递减。

### 4.6 创新点说明（四条，均可核验）

| # | 创新点 | 怎么核验 |
|---|---|---|
| 1 | **用实测 TPOT 反推权重读取带宽**，判定"单请求已到带宽上限"（c1 = 982 GB/s = 峰值的 97.4%），从而确定"只能摊薄读取、不能提速单请求"的优化方向 | §7.2 表 + 基线四档数据 |
| 2 | **区分"配置封顶"与"硬件饱和"**：c8 吞吐不涨但带宽占用仅 57.9%、`Running` 恒为 4、`Waiting` 恒为 0 → 判定为 `max_num_seqs=4` 封顶 | vLLM 日志 + §7.2 |
| 3 | **用 vLLM 自报的并发上限做剪枝**：容量随上下文变化（299,132 @40960 vs 231,303 @16384），剪枝必须按档位取值，否则会把不可行组合当成可行 | §7.1 两个容量值 |
| 4 | **2×2 因子设计**：不做 160 组全组合，先筛主效应再对有主效应的两个因子做全组合，用交互项回答"能否叠加" | §4.5 |

### 4.7 取舍依据（"不做"也要有证据）

### 7.2 瓶颈判断

| 并发 | 折算权重读取带宽 | 占 4090 峰值（1008 GB/s） | 结论 |
|---:|---:|---:|---|
| 1 | 982 GB/s | **97.4%** | 单请求已到带宽上限 |
| 4 | 596 GB/s | 59.1% | 有余量 |
| 8 | 584 GB/s | 57.9% | 吞吐不涨是 `max_num_seqs=4` 封顶，非硬件饱和 |

### 7.3 取舍

| 选择 | 代价 | 理由 |
|---|---|---|
| 用 MTP 提速 | 无（TPOT 同时下降 10%） | 唯一"又快又稳"的优化 |
| 缩上下文到 16k 换并发 | TPOT 恶化 48% | 只在需要更高并发时用；不是性能因子 |
| 保持 fp8 KV | 无 | 实测比 bf16 快 2.2%，且省一半 KV 显存 |
| 不做自做 PTQ | 少一条路线 | 权重装不下 + 工具链不覆盖该架构 |
| 候选只跑 20 请求/档 | 延迟不可与 100 档直接比 | 全跑 100 需 10 小时，窗口只有 6 小时 |
